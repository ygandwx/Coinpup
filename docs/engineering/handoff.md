# 跨环境与跨会话交接

目标：换电脑、工作目录、开发者或对话后，可以仅凭仓库恢复上下文并继续实施。

## 恢复步骤

1. 获取仓库，确认 Git 远端和目标分支。按 `AGENTS.md` 的顺序阅读文档。
2. 检查当前改动和近期提交，例如 `git status --short --branch`、`git log -5 --oneline`。查看当前任务关联的 PR 状态；不能仅凭本地分支名判断已合入。
3. 对照 `docs/engineering/status.md` 确认已实现范围、验证证据和环境限制。若记录落后于代码，先补齐事实。
4. 按 `README.md` 建立环境；仅从安全配置渠道取得运行凭据。新环境验证失败时先区分依赖、配置、服务和代码原因。
5. 选择状态文档列出的下一步，核对路线图依赖；接着已有实现开展工作，不重建已完成模块。

本地未提交文件不会随 Git 迁移。交接前应把需要保留的代码放入可恢复的分支或补丁，并记录位置；凭据、真实账单及数据库备份必须通过独立的安全渠道管理，不加入仓库。

## 在新位置继续的指令

可以向新的开发者或代理提供下面这段指令；具体进度以仓库记录为准，不在指令里复制一份容易过期的功能清单：

> 请继续开发 https://github.com/ygandwx/Coinpup。先读取 README.md、AGENTS.md 和 docs/engineering/status.md，再按其中的顺序阅读路线图、需求和架构。检查当前分支、未提交改动、关联 Issue/PR 及 CI。先简述实际进度与下一项可执行工作，再接着实现；保留已有工作，不重建已完成模块。完成后执行相关验证，并更新 status.md 和关联 PR 的交接信息。

若当前工作还在未合入 PR 中，必须取得该 PR 分支；只下载默认分支可能缺少最新实现。后续位置从 [当前状态](status.md) 的 PR 链接确定分支，不能永久写死某个临时分支。

## 每次交接必须记录

在 `docs/engineering/status.md` 更新以下内容：

| 项目 | 必填内容 |
| --- | --- |
| 当前工作 | 任务编号、目标、分支、PR 链接或尚未创建的状态 |
| 实际完成 | 已实现行为和相关文件；区分文档、占位与可用功能 |
| 验收证据 | 命令、结果、测试范围；关联提交或 CI 链接（如有） |
| 环境限制 | 缺少的运行环境、未执行检查，以及由此尚未验证的能力 |
| 未完成事项 | 具体缺口、失败现象和必要上下文 |
| 下一步 | 可直接执行的顺序、预期结果、相关路径 |
| 决策变化 | 对应需求、API、迁移和 ADR 的位置 |

不在状态文档内记录当前提交自身的 SHA；可引用先前已知提交，或让 PR 与 CI 记录承载当前变更的精确版本。

## 完成标准

- 状态使用“待开始／进行中／待评审／已完成／受阻”；“受阻”必须描述实际依赖及解除方式。
- 子步骤完成不等于整个 T 任务完成。阶段完成还需要满足其全部任务验收条件。
- 切换任务或结束会话前更新记录；保留近期里程碑，较早详细历史可通过 Git 与关联 PR 查询。
- 后续需求变化沿用稳定任务编号，新增任务或明确修订验收条件，避免静默重写历史。
