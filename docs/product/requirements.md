# Coinpup 产品需求基线

更新日期：2026-10-03。本文整理需求讨论中已经确认的产品范围，以及实现这些需求时建议采用的设计约束。

**实现状态：本文是需求基线，不是功能完成清单。已交付增量、实际验证与剩余工作以 [当前状态](../engineering/status.md) 为准；不能把需求条目当作已完成能力。**

- **C（Confirmed，已确认）**：用户在需求讨论中明确选择或确认的产品行为。
- **P（Proposed，设计建议）**：为实现已确认需求提出的模型、规则或工程约束，不冒充用户原话。进入开发时应通过设计审阅确定，并在有冲突时优先遵循 C 类需求。
- **待配置／待核验**：真实公司、基础设施或规则参数尚未提供；不能用示例值代替真实值，也不表示需要重新讨论已经确认的产品范围。

## 2. 已确认的功能需求

### C-01 使用主体与独立账本

- 个人与每家公司在原则上独立记账。
- 公司可以新增多个，各自拥有公司资料、账户、分类、业务记录、票据和相关提醒。
- 有统一主视图，可以按公司查看，也可以任意选择多个公司与个人一起查看。
- 聚合视图支持查看某一分类的汇总费用；原始记录始终保留实际归属主体。
- 第一版只有一位使用者；不能因为只有一位使用者，就把不同主体的账户、分类或账务数据混为一套。

### C-02 分类模板与聚合分类

- 提供公共分类模板，创建个人／公司账本时可以复制使用。
- 复制后，各主体独立维护分类，不随其他主体的修改而变化。
- 支持把不同主体的本地分类映射到统一分类，用于聚合统计。
- 聚合可同时按主体集合和统一分类筛选。
- 同名分类不是同一个数据对象；聚合映射不能改变本地分类、记录归属或原始金额。

### C-03 公司地区、类型和资料

首版包括以下公司：

| 注册地区 | 已确认类型／范围 |
| --- | --- |
| 中国大陆 | 有限责任公司。 |
| 香港 | 有限责任公司。 |
| 美国 | LLC，注册州包括 New Mexico（NM）和 Wyoming（WY）。 |
| 爱沙尼亚 | 私人有限公司。 |

公司资料采用地区模板加自定义字段。公共资料包括法定名称、显示名称、注册地区、公司类型、注册地址、注册编号、税务相关编号、联系方式，以及提醒规则所需的成立日期等资料。

- 根据注册地区显示适用字段和说明，不能给所有公司只显示同一个无差别的“税号”字段。
- 香港商业登记号、中国大陆税务相关编号等需要按地区分别表达。
- 银行账户资料支持账号、开户行等信息；一家公司可以有多个银行账户。
- 保存营业执照、注册证书等公司附件。
- 支持证件到期、年审和税务申报提醒，详见 C-15。
- 自定义字段用于补充地区模板未覆盖的资料。

### C-04 账户、币种与资产

支持账户类型：银行账户、现金、微信、支付宝、信用卡、PayPal、Wise、Stripe，以及记录虚拟货币资产的账户。

- 每个账户支持多币种余额，不把账户限制为一个币种。
- 建立具体账户并记录期初余额；后续收支、转账、换汇和手续费更新相应余额。
- 同一机构的不同币种余额应可分别查看。
- 支持记录账户间资金转移，区分转账与收入／费用。
- 支持的加密资产包括 **USDT、USDC、XMR、BTC、ETH**。
- 加密资产范围为持有数量、收款、付款、转账、手续费及余额估值；不包含交易策略、自动交易或投资盈亏系统。
- 首版通过手工录入与上传账单／票据确认记录，**不需要账户 API 或链上自动同步流水**。

### C-05 日常记账

- 记录收入／支出、金额、原币或资产、支付账户、日期、分类及相关票据。
- 个人记账覆盖生活中的各项收支与支付方式。
- 公司记账支持与客户、供应商、项目、业务单据和付款记录关联。
- 支持一笔业务按多个分类拆分；不能因为拆分类别而重复增加总金额。
- 手工录入与票据确认应避免重复计算收入／费用或造成余额不一致；统一业务模型是 P-03 的实现建议。

### C-06 客户、供应商与项目

- 管理客户与供应商资料。
- 管理项目，按项目统计收入、成本及结余。
- 客户、供应商、项目与对应公司的业务记录关联。
- 该能力面向经营管理，不等同于已承诺完整 ERP、库存、工资或正式财务报表。

### C-07 应收应付与部分收付款

- 记录尚未收到或尚未支付的款项。
- 支持部分收款和部分付款，显示已结算金额与剩余金额。
- 账单和实际收付款需要关联，不能上传账单一次、导入对应流水又计算一次收入／费用。
- 一张业务单据可以分次收付款；具体匹配模型见 P-03。

### C-08 报销、代付与主体间往来

- 支持用户或员工垫付费用，记录是否已经报销；首版由同一使用者管理，并不引入员工登录或审批流程。
- 支持个人替公司支付、公司替个人或其他公司支付，以及主体间资金往来。
- 此功能可以手动选择是否开启。
- 能关联垫付与偿还记录，显示谁应向谁偿还多少。
- 聚合时处理已经关联的内部转账、报销与偿还，避免重复计算费用。
- 支持内部交易的展示开关；合并处理应基于用户所选主体集合，详见 P-04。

### C-09 票据、账单与本地 OCR

上传资料主要包括：

- 银行／信用卡月结单 PDF：一份文件可能包含多笔交易。
- 供应商账单／商业 Invoice PDF：一份文件可能对应一笔应付款。
- 发票、收据等照片。
- 文件通常为中文和英文。

处理流程：**上传 → 本地识别 → 待确认 → 修改或拆分 → 用户确认入账**。

- OCR 必须运行在用户自己的服务器上，原始文件不发给外部 AI／OCR 服务。
- 识别结果可以修改归属主体、账户、日期、金额及分类，再批量确认。
- 用户可以选择是否将一张发票拆分为多个分类。
- 原始文件作为附件保存，能够回看并核对。
- 应提示疑似重复资料或记录，避免重复入账；自动关联与重复判断的具体交互见 P-03、P-05。
- 首版不因识别置信度高而跳过用户确认。

### C-10 商业 Invoice

- 只生成商业 Invoice，不涉及中国税务发票开具或查验。
- 支持公司 Logo、自动编号、中英文模板、客户资料、商品／服务明细、币种、折扣、手工填写税率、到期日、收款信息和 PDF 下载。
- 支持手动创建。
- 支持周期性生成**草稿**，由用户检查后继续处理。
- 不因周期性生成而直接把草稿当成已收款；草稿的账务状态见 P-03。
- 尚未要求自动把 Invoice 邮件发送给客户。已确认的邮件功能是提醒。

### C-11 现金与经营两种统计视角

- 保留实际收付款日期与收入／费用所属期间。
- 现金收支按实际收付款查看。
- 经营收入／费用按归属期间查看，同时可看到未结算状态。
- 例如 9 月归属的账单在 10 月付款，经营费用属于 9 月，实际付款发生在 10 月。
- 两种视角不能相加形成另一份“总费用”；它们是同一业务的不同观察方式。
- 代付场景进一步区分费用归属主体与付款账户所有者，见 P-04。

### C-12 原币、展示币与估值

- 默认按原币种分别展示，不把不同币种的数字直接相加。
- 可以统一切换为 **美元 USD、英镑 GBP、欧元 EUR、港币 HKD、人民币 CNY** 查看折算结果。
- 收支统计默认采用交易日历史汇率。
- 当前账户余额默认采用最新汇率／行情。
- 两种估值口径可以随时切换，并始终保留原始币种与金额／资产数量。
- 允许服务器访问公共汇率及加密资产行情服务并自动更新。
- 离线时使用缓存行情，显示缓存价格的时间。
- 公共行情联网许可不改变本地 OCR 的隐私要求。

### C-13 Web

- 首版 Web 联网使用，不要求实现 Web 离线记账。
- 支持桌面浏览器及手机网页布局。
- 手机网页应方便快速记账和上传照片／文件。
- 界面支持中文与英文切换；切换界面语言不修改原始业务资料。

### C-14 后续 Android／iOS App

- 复用后端业务能力和接口，避免另建一套独立财务逻辑。
- 支持离线新增、拍照、查看已缓存历史、编辑及删除记录。
- 恢复联网后同步数据及待上传附件。
- 离线历史查看基于本地缓存，不等于已经承诺自动下载全部历史附件。
- 同步需要处理重试、冲突和删除传播；具体约束见 P-08。

### C-15 站内与邮件提醒

- 同时提供站内提醒和邮件提醒。
- 包括公司证件到期、年审，以及税务申报提醒。
- 根据地区、公司类型、成立日期及所需资料自动推算适用日期，也支持手动设定或覆盖。
- 自动日期规则的适用条件、版本及缺失参数处理见 P-07。
- 不可仅凭“同为 LLC”推定 NM 和 WY 规则相同，也不可仅凭成立日期推定全部税务义务。

### C-16 部署与隐私

- 部署目标是用户自己的高性能物理服务器。
- 票据和公司证件保存在该部署控制下，本地完成 OCR。
- 允许获取公开汇率／行情，允许通过配置的邮件服务发送提醒。
- 当前不需要估算服务器采购预算；操作系统、域名、邮件配置等在部署时确定。
- 性能、识别准确率和吞吐量仍需用实际服务器与样本验证，不因“高性能服务器”直接给出未经测量的承诺。

## 3. 建议的业务模型与实现约束

本节均为 **P 类设计建议**。其目的在于使已确认行为可实现、可审计、可恢复，不代表这些能力已经完成。

### P-01 主体与账本模型

建议使用 `Workspace → Entity（个人／公司）→ Ledger → Account → Currency/Asset Balance`。

- Workspace 初期只有一个使用者；所有业务数据仍需有明确归属和访问边界。
- 每个主体先建立一个主要账本；“每个主体任意多个账本”不是已确认的首版要求。
- 账户、分类、项目、客户供应商、单据和附件明确关联归属主体；跨主体关系使用显式关联。
- 公共分类模板以复制方式初始化；统一分类映射作为报表层关系，未映射项单列提示，不自动归入同名项。
- 地区资料用公共字段、地区模板、自定义字段组合实现。

公司标识字段的候选设计需要在实现前核验官方含义。例如分别表达大陆的统一社会信用代码／税务标识、香港商业登记号及适用的公司标识、美国州登记标识与 EIN、爱沙尼亚登记代码与适用的 VAT 标识；**这些候选字段不构成对每家公司必须具备哪些编号的判断**。

### P-02 金额、账户与账务一致性

- 内部以复式分录或等价的可验证记账结构维护余额，前台保持简单的收支操作。
- 每个账本设置记账基准币；原币金额／资产数量和基准估值分开保存。展示币种切换不改变账本基准币或历史记录。
- 采用高精度 Decimal／定点数，不用二进制浮点数存储或计算金额；API 以不会丢失精度的形式传输。
- 币种／资产有独立精度规则，不把全部金额截为两位小数。网络与代币精度按配置表达，不能根据同名代码随意合并资产。
- 账户余额来自一致的入账记录；期初余额、转账、信用卡还款和往来结算不冒充收入／费用。
- 跨币种转账保存转出数量、转入数量、成交汇率和手续费；不能直接把不同币种的数字相加配平。
- 信用卡账户应区分负债余额与可支用资金；额度管理不是已确认的首版要求。
- 历史报价与最新报价记录来源、有效时间和获取时间。缺少报价时标注不可估值，不用 0 或随意的最近日期冒充准确值。
- USDT、USDC 不写死等于 1 USD。显示估值不自动构成加密资产交易或投资盈亏核算。

### P-03 单据、付款与分摊

建议将业务拆成 `Document + DocumentLine`、`Payment/Transfer` 和 `Allocation`：

- 单据描述发生了什么业务；分类行保存分类、项目及归属期间。
- Payment 描述真实资金结算；Transfer 描述资金在账户之间的移动。
- Allocation 表达一次付款结算哪些单据、每张单据被结算多少，支持多对多。
- 分摊不再产生一次账户余额变动；不能同时累计单据金额和对应付款金额为费用。
- 跨币种分摊同时保存单据币种结算数量和付款币种数量；手续费单独表达。
- 超额或未分配收付款作为显式的预收／预付或待分配余额处理，不静默超额结清单据。
- 银行流水匹配已有付款时只关联来源证据；建议匹配结果由用户确认，不静默合并或删除记录。
- 草稿不计入应收应付、经营收入／费用或现金收支；用户确认形成有效业务单据后才按相应状态统计。
- 周期 Invoice 的周期实例使用稳定幂等键，失败重试不能多生成一张草稿。
- 退款、贷项、作废、修改和撤销需要可追溯记录，保证原单据、结算状态和余额一致。

### P-04 代付与合并统计

费用归属主体、付款账户所有者、需要偿还的主体分别记录。

例如个人替公司支付 100 CNY：公司费用为 100，个人生活费用为 0，公司对个人形成 100 的待偿还往来；之后公司偿还只结清往来，不再计一笔费用。合并查看时，对外费用始终为 100。

- 个体账本里，转账、借款及报销偿还本来就不是经营收入／费用；不能等到聚合后才修正其分类。
- 账户现金流按真实付款账户统计；按业务归属统计的已付款费用需要另有清晰标签，不能冒充公司自己的银行现金流。
- 双方主体都被选中时，合并资金流可排除其已关联的内部转移；只有一方被选中时，仍保留该主体的实际资金变动，并标为往来或转账。
- 个人代付给外部商家的付款仍是对外付款，不能因为存在内部偿还关系而被一并抵销。
- 真正的内部销售／采购按明确关联和展示开关处理；只有双方都在所选主体集合时才做对应合并排除。
- 只有匹配并确认的内部关系才能用于抵销。金额相同、日期接近或同名对手方只能作为提示线索。
- 关闭往来功能不应删除历史关系；未关联记录不能被承诺自动抵销。

### P-05 文件与 OCR

- 原始文件、解析结果、识别任务与最终业务记录使用独立标识并保留关联。
- 对有文本层的 PDF 优先提取文本；扫描 PDF／照片进入本地 OCR，保留页码或来源位置便于核对。
- 任务可以异步运行并显示状态；单页失败、超时或重试不直接产生财务记录。
- 文件哈希识别重复文件，业务字段识别疑似重复交易；重复提示不能替代用户判断。
- 一张发票的分类拆分金额必须与入账总额一致；识别金额不确定时必须由用户校正。
- 不把原始票据、公司证件、OCR 文本或账户明细上传外部模型；公开行情请求只携带必要的公开查询参数。

### P-06 Invoice 与编号

- 计价采用用户于2026-10-09确认的方案A：未税单价×数量，扣除行折扣金额，按币种精度逐行四舍五入得到未税额，再按手工税率计算并舍入行税额；总额累加已舍入的各行，不对整单重新计税。行折扣不超过精确的数量×单价；不提供含税计价模式或整单隐式折扣分摊。技术边界见[ADR0026](../architecture/decisions/0026-draft-pricing.md)。

- Invoice 按公司隔离编号规则、模板、Logo 和收款信息，编号唯一性在对应公司规则内校验。
- 周期规则明确时区、周期起点和下次执行时间；生成草稿与正式编号分配的具体时机在实现设计中确定。
- 调整或停用周期规则不会改写已经确认的历史 Invoice。
- PDF 内容、系统保存的数据及语言模板相互一致；税率是手工输入值，不据此推断完整税务申报结果。

### P-07 提醒规则

- 规则包含地区、公司类型、适用条件、所需参数、来源、版本和更新时间。
- 系统按已知规则与用户配置推算日期，用户／其会计确认适用事项；“推算日期”不扩展成自动判定全部纳税义务。
- 参数可能包括成立日期、财政年度、上次续期、税务登记状态等，按规则需要收集；不能仅凭公司类型猜测。
- 缺少参数或尚无核验规则时，显示待补充／待确认，并支持手动日期，不生成假定准确的法定截止日。
- 用户覆盖的日期优先，保留系统计算值及覆盖记录；规则更新不静默覆盖人工设定。
- 提醒状态可追踪；发送失败可以重试，同一到期事件、同一提醒时点、同一渠道不重复发送。
- 收件邮箱、提前天数和实际 SMTP 信息在部署／设置中配置。
- 法规自动抓取并自动修改规则不是已确认能力；首版可用经过核验的版本化规则随系统更新。

### P-08 App 同步与可恢复编辑

- 第一阶段就保留稳定记录 ID、版本、幂等键、修改游标及删除标记，第四阶段实现完整同步行为。
- App 使用本地数据库与 outbox 保存离线操作；附件单独排队上传。
- 建议在附件恢复联网并上传后执行服务器 OCR；手机离线运行完整 OCR 模型不在已确认范围内。
- 服务端按增量游标提供变化；同一请求重复提交不重复记账。
- 两端修改同一记录时保留双方版本并呈现冲突，不采用无提示的最后上传覆盖。
- 删除通过 tombstone／等价机制传播，防止旧设备把已删除记录重新创建。
- 已入账记录的修改和删除保留审计轨迹，并通过冲销／替代或等价原子操作维护金额、分摊及余额的一致性。
- 同步成功、业务确认入账、附件上传完成分别有明确状态；不能在实际未持久化时提示全部成功。
- Flutter 是后续 App 的当前技术建议；用户确认的是 Android／iOS、离线范围和联网同步，具体工具版本不是产品承诺。

### P-09 安全、备份与运行基础

- 登录、访问检查、密钥配置和日志脱敏从工程地基开始建立，不延后到正式上线前临时补做。
- 附件下载需要有效授权；票据和公司证件不作为公开静态资源暴露。
- 备份覆盖数据库、文件及必要关联元数据，验证能恢复，而不只验证生成了备份文件。
- 在第一阶段建立备份与恢复冒烟验证，第三阶段完善定时备份、保留策略及完整恢复演练。
- 迁移、后台任务、周期生成和提醒发送需要幂等及故障恢复策略。
- 恢复和升级后要核对余额、单据结算、附件引用及提醒状态。
- 不保存加密资产私钥或发起链上付款；本产品当前范围是记账。
