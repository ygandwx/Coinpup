# ADR 0003：资产身份、精确数量与数据库边界

- 日期：2026-10-03。
- 状态：T02 首个增量；执行与集成证据见[项目状态](../../engineering/status.md)。
- 对应：需求 C-04、P-02；验收 A-07 的底层精度部分。

## 问题

同一账户需要保存多个币种和加密资产。ETH 的 18 位小数不能经过二进制浮点数，也不能依赖默认只有 28 位有效数字的 Python Decimal 运算上下文。不同网络上的同名代币不能直接相加。数据库的 NUMERIC 列会先把超过列 scale 的输入舍入，因此单靠列类型无法保证拒绝失真输入。

## 决定

### 不可变资产定义

资产具有稳定身份、代码、种类、精度，以及适用的网络和代币标识。内置 USD、GBP、EUR、HKD、CNY 为 2 位，BTC 为 8 位、ETH 为 18 位、XMR 为 12 位。五种法币是统一展示币种的要求，不能误解为唯一允许记账的原币；其他法币可显式配置三位 ASCII 大写代码和精度，内置定义不得改写。配置功能不等于已实现权威 ISO 货币目录或自动验证币种元数据。

USDT、USDC 必须显式提供网络、代币标识与精度；本增量不预置未经核验的链或合约地址，也不调用链上接口。

同代码不同网络属于不同资产。金额运算必须使用相同且一致的资产定义，不能仅按代码相等判断。资产一旦被引用，未来资产目录的更新不得原地修改精度或身份；持久化目录及此约束将在账务 schema 增量落实。

### 数量与传输

`Amount` 内部保存整数最小单位，提供同资产加、减及取负；所有入口和运算结果都校验范围。整数运算不使用浮点数，也不读取或修改 Decimal 的全局上下文。转换为数据库 Decimal 时从精确字符串构造。

外部数量只接受 ASCII 十进制字符串：`-?(0|[1-9][0-9]*)(\.[0-9]+)?`。拒绝 JSON 数值、布尔值、空白、千分位、指数、非有限值、Unicode 数字及超过资产精度的输入；多余小数位即使为零也拒绝，避免客户端悄悄依赖舍入。输出固定为资产精度，负零统一为零。

数据库解码独立于外部输入：接受 PostgreSQL 返回的 Decimal 和补齐的无损尾零，例如 USD `1.230000000000000000`，但拒绝超出资产实际精度的非零位。不把外部 API 的严格字符串入口直接套在数据库返回值上。

### 存储边界

本增量定义 PostgreSQL `NUMERIC(38,18)` 合同：最多 20 位整数、18 位小数，绝对值严格小于 `10^20`。任何资产精度不超过 18；未来要支持更大精度时必须显式迁移并扩展契约，不能截断。

在 SQLAlchemy 绑定参数前验证金额，拒绝原始浮点数、错误类型和超出边界的数量。数据库解码再次核对数量；SQLAlchemy 的校验并不保护绕过应用直接执行的 SQL，未来业务表仍需要适用的约束与权限。

本次只用 PostgreSQL 临时表验证精确往返及绑定拒绝，不新增业务表或迁移。资产列与数量列的归属、资产目录不可变性、外键和事务约束由后续账务 schema 实现，不能把此临时表当成已交付的账本。

当前 `AmountNumeric(asset)` 绑定一个已知资产，适合验证数值存储合同；它不能从行内自动推断资产。后续多币种分录必须使用明确读取行内资产定义的写入边界，不能按币种不断增加列，也不能脱离资产校验直接绑定原始 Decimal。

绑定类型只支持本项目的 PostgreSQL + psycopg 驱动；其他驱动及 SQLite 未经此精度合同验证，明确拒绝，不能用 SQLite 的浮点转换来证明 PostgreSQL 的数量精度。

## 示例与边界

- ETH `1.000000000000000001` 完整往返；BTC `1 - 0.1 - 0.00001 = 0.89999000`。
- USD `0.001` 被拒绝；USD 与 EUR、两个网络的 USDT 相加被拒绝。
- 金额相等比较包含完整资产定义及最小单位；不同资产相等比较返回 false，排序和算术拒绝。资产停用不改变既有数量身份，仍可解码历史；新字符串输入拒绝停用资产。
- `100 USD → 90 EUR` 加 `2 USD` 手续费仍是三个真实数量。本金额类型不计算汇率、不自动配平换汇，也不提供账户余额。
- 汇率、乘除运算、舍入政策和估值留给对应业务增量；不得用本次固定小数输出改写历史数量。

## 验证与影响

测试覆盖最小单位、最大边界与溢出、无效输入、负零、跨资产拒绝、外部 Decimal 上下文被改变时结果仍一致，以及真实 PostgreSQL 往返与写入前拒绝。A-07 的账户、API、手续费分录和余额流程尚未实现，因此该完整案例保持待验收。

没有新增依赖、环境变量或生产迁移。后续业务服务通过此公共金额边界处理原始数量；前端和 App 仍必须传输字符串，不得先转换为 JavaScript Number。

## 设计依据

- [PostgreSQL 17 数值类型](https://www.postgresql.org/docs/17/datatype-numeric.html)：NUMERIC 的 precision/scale 范围以及超 scale 输入的舍入行为。
- [Python 3.12 Decimal](https://docs.python.org/3.12/library/decimal.html)：十进制构造与算术上下文的区别。
- [Bitcoin 术语](https://developer.bitcoin.org/glossary.html)、[Ethereum Ether 单位](https://ethereum.org/developers/docs/intro-to-ether)、[Monero 技术规格](https://docs.getmonero.org/technical-specs/)：基础资产最小单位。
- [ERC-20](https://eips.ethereum.org/EIPS/eip-20)：代币精度由代币定义，不能按显示代码推断。
