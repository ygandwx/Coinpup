# ADR 0008：更正、撤销与不可变历史

- 日期：2026-10-03
- 状态：采用；执行证据见 [当前状态](../../engineering/status.md)
- 任务：T02-6 / T03，接续 [原子入账](0005-atomic-posting-and-receipts.md) 与 [本金和手续费](0007-exchanges-and-explicit-fees.md)

## 稳定业务身份

一条财务业务始终使用同一个 `FinancialOperation.id`。更正增加版本，在同一事务中完整冲销上次入账，再写入替代分录。撤销增加版本并完整冲销，状态变为终止的 `cancelled`。旧分录、金额和原始命令回执不更新、不删除。

例如期初 1000 USD、支出 100 USD，更正支出为 120 USD 后余额为 880 USD、累计费用为 120 USD；撤销后余额回到 1000 USD、费用为 0。历史保留最初支出、冲销、更正及最终撤销。

`current_journal_id` 指向最近一张正常入账凭证；撤销后保留该指针，用业务状态、最新版本与对应冲销凭证表达撤销结果。查询最新入账内容不能代替求和全部账户分录计算余额。

操作种类保持不变。期初更正只允许修改数量、日期和描述，账户与资产固定；期初占用标记在撤销后保留，不能通过新键或旧设备重新建立同一位置。恢复已撤销业务不属于本接口，应创建新的普通业务；期初恢复须另设显式流程。

## 回执与当前状态

原五种新增 POST 的响应和持久回执保持不变，包括无费用 JSON 形状和请求摘要。新增成功后，即使后来已经更正或撤销，重复原命令仍返回当时的 201 回执，不代表业务仍处于旧状态。

在业务网页和移动客户端发布前，明确调整 GET 单条/列表合同，返回 `OperationState`：

- 稳定 `id`、`ledger_id`、`kind`、当前 `version`、`status` 和 `updated_at`。
- `latest_posting` 使用原有按 `kind` 判别的财务响应，包含最近正常入账的金额、分类、费用及凭证版本。
- 已撤销状态另外包含 `cancellation`：撤销版本、反向凭证 ID、原因及记录时间。

撤销时外层版本高于 `latest_posting.version`，后者始终来自该凭证自身版本。列表默认保留所有状态，支持显式状态筛选。客户端在重试得到回执后重新读取当前状态，不能拿历史回执覆盖更新的业务状态。完整请求/响应字段以实际 OpenAPI 为准。

## 修改命令与并发

在 `/api/v1/ledgers/{ledger_id}/operations/{operation_id}` 下新增：

- `POST /corrections`：`expected_version`、非空 `reason`、带 `kind` 的完整 `replacement`；替代内容禁止提供新 ID。
- `POST /cancellations`：`expected_version`、非空 `reason`。
- `GET /history`：按版本返回创建、更正、撤销及相关不可变凭证和精确有符号行。

两种修改命令复用 Cookie、Origin、CSRF 和必填 `Idempotency-Key`，成功返回 200 当前状态，并持久保存这一响应供后续重放。原因去除首尾空白，长度 1–1000，不能含空字符。新请求必须匹配当前版本且业务仍有效，过期编辑或修改已撤销记录返回冲突。

修改摘要包含动作、账本、路径中的业务 ID、预期版本、原因及完整替代内容，保留金额字符串。相同键对应不同业务或不同动作也冲突。权限与账本归属验证后先检查回执，再检查当前版本、归档和新目标状态；已成功命令不会因后来的修改或归档而无法安全重试。

## 事务与精确冲销

锁定账本并使用同一事务，先验证全部替代内容和最终余额，再追加冲销/替代分录、更新业务版本和状态、保存回执。任何一步失败都不留下部分金额、版本或幂等记录。

反向凭证逐行复制上次正常入账的行号、组成部分编号、资产、角色、账户和分类，数量精确取反，包含全部手续费及换汇对方行。使用整数最小单位或精确 Decimal 取反，不能受默认 Decimal 上下文精度影响。反向费用的符号与正常费用相反，因此按原凭证逐行对应验证，不能套用新增费用的正负规则。

冲销沿用被冲销凭证的交易日、业务归属日和描述；本次实际记录时间及原因单独保存。这样更正移除原期间的旧事实。实际退款应作为新的业务处理，不能假借更正日期改变退款发生时间。

原账户、分类、资产及资产关联归档或停用后仍允许冲销；替代内容的全部新引用必须符合当前有效性检查。账本主体归档仍暂停新修改，恢复主体后再执行。最终余额检查合并反向与替代的全部账户增减，包含手续费，避免对临时中间余额误报溢出。

## 数据库不变量与历史

业务身份、种类、归属、创建人和创建时间不可变；仅允许从有效状态以版本加一方式更新头指针/状态，已撤销状态不能恢复，操作不能删除。凭证和行的不可变及封存保护保留。

数据库验证连续完整的版本链：首版只有正常入账；每次更正恰有一张对上一入账的精确冲销和一张新入账；最终撤销只有冲销。每张入账最多被冲销一次，不能跨业务或账本引用。头指针必须匹配最近正常入账，撤销状态必须对应最新冲销。新入账按已有各类形状检查，冲销按完整逆向对应检查。

`Journal.revision_reason` 首版为空，后续版本必填；同次更正的两张凭证原因一致。当前单用户拥有并执行其账本业务，历史执行人来自操作创建人；以后引入多用户时需扩展逐次执行人字段。历史按版本聚合，正常/反向行都返回精确字符串，不能把反向行误读成新的正数费用。

迁移增加状态和原因字段，旧业务为有效首版，历史内容不变。降级若存在更正或撤销历史就拒绝，不能删除历史后强行回退。状态和稳定版本是后续删除传播的保留标记；增量同步游标、设备及离线冲突解决仍由 T11 实现。

## 验证边界

检查包括支出 100→120→撤销、换汇及多资产手续费完整逆向、归档旧引用可冲销、无效新目标整笔回滚、极值与最小单位、并发版本冲突、相同键重试、不同路径/动作键冲突、旧创建回执重放、封存和原始记录不变、撤销终态及期初标记保留。备份恢复需保留版本链、原因、精确行、状态与所有历史回执。

API 和数据库测试不代表网页修改流程已完成；T04 接入实际表单、冲突提示和历史展示后再验收完整用户流程。
