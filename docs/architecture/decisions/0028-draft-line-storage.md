# ADR 0028：精确草稿行与整单约束

- 日期：2026-10-09
- 状态：已采纳（ADR0026/0027的行存储技术细化）。
- 关联：[计价](0026-draft-pricing.md)、[表头](0027-draft-header-storage.md)。

## 背景

原business_document_lines只有被分录引用的身份。草稿需要分类、项目、归属日及方案A的原始输入和可复核金额，且任何行变化必须同整张草稿一致。不得把旧分录引用补造成新业务行。

## 决定

1. 原行追加可空资料。旧身份所有新列保持SQL NULL；新完整行保存单据内正整数line_no、描述、完整asset_id、原始quantity/unit_price/discount_amount/tax_rate_percent字符串、分类/类型、可选项目、归属日、分类/项目快照和NUMERIC(38,18)净额/税额/合计。完整与匿名模式不可互换，不允许半配置行。
2. 单据、分类及项目采用同账本复合外键，分类同时匹配income/expense类型，资产采用完整身份外键；所有引用RESTRICT。序号在单据内唯一且创建后不改，新行由服务分配未使用的递增序号。移除使用归档，已有序号不复用；界面按序号排序，允许间隔，不在本包增加拖拽重排。
3. 数据库按冻结的方案A验证输入语法/长度、资产精度、正数量、非负单价/折扣/税率、折扣上限及精确净额/税额/合计。税额用精确十进制乘法和最终舍入，不先做有限精度的中间除法。服务继续调用纯整数计价模块，客户端提供的合计不是事实来源。
4. 完整行只允许写入draft父单据；旧匿名行继续原行为。新增延迟约束在提交时核对整单最终状态：有效行必须完整、同父单据资产，Invoice行用income分类、bill行用expense分类；最多200个有效行，合计不能超过Amount存储上界。空/零草稿允许，归档行不参与合计但保存原资料。
5. 整单服务先按咨询锁→账本→主体→资产锁序校验所有者、活动状态和expected_version，再原子修改表头/行；任何行修改或归档都使父版本增加一次，子行自身版本依旧逐次增加。此协议由保存服务实施并作并发测试，不为每个草稿另建财务回执；未知结果和显式冲突核对沿用ADR0025。模型包尚不开放HTTP写入口。
6. 不删除行，禁止改UUID/账本/父单据/创建时间/序号、跳版本或抹掉完整资料。分类/项目改名不自动更新保存的快照；草稿用户明确刷新才改。确认后的行将由后续确认状态机封存，不通过草稿接口重写已入账历史。
7. 表头/行沿用现有变更日志。降级遇到任何完整行（含归档）即拒绝；空资料降级恢复0016的冻结身份保护，旧行、分录及通知逐值不变。隔离旧迁移探针按依赖卸载/恢复新迁移，不改原约束断言。

## 影响

真实PostgreSQL验证原字符串、不同资产精度与整数计算器一致、临界舍入、伪造金额、跨账本引用、方向/资产不匹配、200行和总额边界、身份与迁移保护。完整bundle恢复核对原输入、结果、快照、分类/项目和旧回执。后续整单服务/API与网页完成后才验收T06-2。

## 备选方案

只存JSON或客户端合计无法提供关联和金额约束；只保留数值会丢失原输入。对每行单独入账会把草稿变成财务事实；单独更新子行而不提升父版本则会破坏整单并发检查。
