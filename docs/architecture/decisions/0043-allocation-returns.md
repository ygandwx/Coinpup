# ADR 0043：追加式分摊退回

- 状态：已采纳（技术细化；跨币种部分数量规则待用户确认）
- 日期：2026-10-14
- 依据：P-03、B-11、ADR0008/0040/0041，用户已确认的手动贷项净额/税额。

## 背景

已确认单据、付款及分摊都是不可变来源。真实退款或贷项可能需要释放已应用本金；直接删除分摊或修改已付金额会破坏原回执与恢复。原0031容量按所有正分摊汇总，尚不支持已释放数量再次应用。

## 决定

- 先引入独立的分摊退回组及有序来源映射；每行明确引用原BusinessAllocationLine并填写payment_amount与document_amount，不修改原Payment、Allocation、源行、凭证或旧JSON回执。
- 两种数量都为正、同资产相等，累计退回均不超过对应原源行。跨资产全额退回保留原两边的完整数量；部分退回的比例/手动口径已集中向用户询问，尚未决定，不能把候选写成已批准或开放未定路径。最多200行，同组来源不重复，全部引用同账本/付款/往来。
- 生效日明确填写并不得早于各原应用日，沿用来源日期下界与开放期间检查；这也保证不早于原付款及开票日。历史更正/取消的原日期规则仍按ADR0008处理。
- 退回是新的往来重分类，按明确开放期间的生效日追加正常凭证；复制原控制身份及源行维度，按实际退回数量逐资产配平。只恢复预收/预付并减少已应用量，不移动资金、不计经营收入或费用、不退还原手续费。错误原分摊的整单更正/取消另按ADR0008保持原日期及版本链，不能用本入口伪装。
- 新命令使用稳定组UUID、原JSON v2及永久账本键；完整回执含有序原分摊来源和所有新操作/凭证。未知提交只重放原意图。成功回执重放先于当前版本、归档、容量和期间检查，复核不可变原来源，不用当前余额证明成功。
- 独立POST `/business-allocation-returns`，正文id、payment_id、return_date、非空reason及有序lines；每行source_allocation_line_id、原应用操作expected_version和两种数量。回执kind为business_allocation_return，含组/账本/付款ID及每行原映射、单据/源行、新操作/凭证ID，不复用旧business_allocation回执或给旧回执补字段。新凭证kind使用长度合法的unallocation，既有普通财务命令联合不扩展。
- 咨询锁→账本→主体→完整排序资产集合，随后读原不可变映射和新快照容量；与付款/分摊共用READ COMMITTED写入约定。同键并发只执行一次，所有成员、回执、日志同事务提交，失败全回滚。
- 当前付款已应用量与单据已结算量改为正分摊减明确退回；旧记录及原初始回执不重写。新分摊和数据库延迟容量校验必须使用相同净量，允许明确释放后重新应用，不能把原正分摊总量放宽为无上限。
- 新业务表有同账本复合外键、不可变保护、changes通知及严格有序完整回执约束。新增独立形状函数，原五类/应计/付款形状和历史冲销校验不改。净容量扩展保留原错误合同，无退回记录时与旧逻辑完全等价。
- 冻结SQL迁移，有新退回历史时拒绝降级；空历史降级恢复0031的原容量SQL并删除新增对象。所有既有constraints测试保持原样。

## 影响与依赖

付款证据采用ADR0042；本决定不改变其原回执或恢复约定。按纯契约/计划、存储约束、事务/净容量、API与双语原意图控制器、浏览器和bundle验收拆包；不开放未受完整约束的写入。

贷项继续按用户明确填净额/税额，真实退款是新的资金事实；两者后续使用本能力原子协调，不能把单独退回当作已经退款。退款、贷项、整单更正取消的完整决定另落ADR，本决定不代替其完整规则或验收。

## 备选方案

删除/覆盖原分摊会丢失永久来源；重写原Payment回执破坏未知提交恢复；仅冲回资金不释放应用会产生负的可用本金；仅放宽原容量断言会允许超额。追加明确数量、单独来源和严格净容量可以保留旧事实及逐资产一致性。
