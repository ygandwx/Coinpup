# ADR 0015：按提交顺序追加变更日志

- 日期：2026-10-04
- 状态：采用

## 背景

后续离线同步需要完整的修改通知和归档标记。PostgreSQL identity 按分配次序取号，晚提交的小序号可能被已推进游标的客户端漏读。系统仅有一个管理员，各主体和账本仍需独立归属；现有财务事实、版本及回执不能改写。

## 决定

- 在 `coinpup_api/sync/` 增加只追加的 `change_log`：`seq bigint identity`、所有者、可空账本、对象类型/文本身份/版本、upsert/archive/restore/cancel 和时间；数据库触发器拒绝 UPDATE/DELETE。
- 九张表的 AFTER INSERT/UPDATE 触发器记录变更：entities、ledgers、accounts、account_assets、categories、assets、financial_operations、stored_files、operation_file_links。失败事务不留下变更，identity 允许回滚空洞。
- 使用固定的单所有者事务咨询锁键 `0x434F494E505550`。每个业务写事务先获取咨询锁，再查询所有者和获取账本、主体、资产及其他业务锁；只读事务不获取它。触发器在 INSERT change_log、分配 identity **之前**再次获取同一把可重入锁，不能依赖 log 的 BEFORE INSERT 触发器在默认值计算之后才锁定。
- 变更只由业务触发器产生；不提供写日志 API。直接向日志注入记录须被拒绝，避免绕过分配顺序保护。
- 资产属于全局单管理员目录，使用文本资产 ID、可空账本；管理员建立前的内置资产种子不产生日志，首次全量读取仍包含整个目录。主体本身也使用可空账本。
- account_assets 没有独立 UUID 或版本：使用 `account_uuid:asset_id` 的稳定文本身份（固定 UUID 前缀与其余完整资产 ID），版本引用触发时的父账户版本；不增加或改写现有列。此事件要求重新读取父账户，不能仅凭父版本相同就丢弃关联变更。
- `GET /api/v1/changes?after=0&limit=100` 复用会话鉴权和服务所有者校验，按 seq 升序读取该所有者的变更。返回 `changes` 与 `next_cursor`；seq/游标采用十进制字符串，避免 JavaScript bigint 精度丢失。limit 上限 200。
- 非空页的游标只推进至最后实际交付的序号；空页保留输入游标，不能使用 identity 当前值或未交付的全局最大序号推进。
- 首次同步先取得起始游标，再读取全量对象，最后从该游标重放后续通知。通知是重新读取当前记录的提示，不是财务事实或完整离线冲突协议；允许全量和增量重叠，按对象更新本地状态。
- 归档、停用和取消保留原记录，用相应 change_kind 表达；恢复为 restore。硬删除不属于现有业务 API。
- 日志、identity 状态和原件随 bundle 恢复。PostgreSQL 序列不受 MVCC 快照约束，导出期间的写入可使备份的序列值领先于可见日志；恢复值须不低于可见日志最大序号，新写入须超过恢复的序列值。已包含在恢复快照内的游标继续有效；恢复到更早快照后的设备协调留给完整同步协议。
- 本包 downgrade 先获取同一咨询锁，已有日志时拒绝删除；空日志才可移除触发器/函数/表，不能丢弃已发布游标。迁移在暂停写入的维护窗口执行。

## 影响

单管理员的业务写入按事务串行，读接口保持原事务行为。序号不是金额、凭证版本或账本合计；重复读取通知不应重新入账。现有 schema 和响应保持，仅新增日志表与读取接口。

新增业务表必须接入变更触发器，沿用先咨询锁再业务锁的顺序。队列计算等长任务在事务外运行，最终业务更新才获取写锁；此决定不实现设备、离线写入或 OCR。

验收覆盖九表插入/更新、归档恢复/取消、完整事务回滚、所有权、游标分页、先分配后提交并发、只读不等写锁、恢复后续号及受保护降级；原约束和财务回执测试继续保留。

## 备选方案

- xid8 与快照 xmin 的无锁游标：可避免写入串行，但游标、快照和分页更复杂；当前单用户系统采用咨询锁。
- 应用层单独记录通知：容易漏掉原始 SQL 或新写路径，且不能天然随事务回滚；采用数据库触发器作为最终保证。
- 为 account_assets 增加独立版本：会改变现有数据库语义；使用稳定复合身份及重新读取父账户保留现有结构。
