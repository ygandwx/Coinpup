# ADR 0001：采用模块化单体与独立本地识别 worker

- 日期：2026-10-03。
- 状态：采纳为 Coinpup 的技术方向；按 T01–T12 分阶段实现。
- 当前交付：首个工程基础 PR 的健康 API、配置、SQLAlchemy 连接和空 Alembic 基线；本 ADR 不宣称业务、鉴权或同步已经实现。
- 关联：[需求基线](../../product/requirements.md)、[架构概览](../overview.md)、[路线图](../../engineering/roadmap.md)。

本文的“首个 PR/当前交付”描述最初基础增量的历史边界。后续管理员、会话与运行基础由 [ADR 0002](0002-administrator-session.md) 补充；最新代码和验证状态见进度文档，不以历史描述否认后续已实现能力。

## 背景

Coinpup 服务于一位使用者，统一管理个人和多家不同地区公司的财务。各主体独立记账，又需要组合汇总；业务包括多币种账户、加密资产数量、票据识别、应收应付、代付报销和商业 Invoice。

用户要求自行部署、本地 OCR、中文与英文界面，先交付联网 Web，后续 Android／iOS App 支持离线查改增删与拍照同步。公开行情允许联网获取，票据不能发送到外部 OCR 服务。

财务操作经常需要同时更新账户变动、单据结算及主体间往来。首阶段需要建立一套明确的数据事实与事务边界，再扩展页面、后台作业和移动端。

## 决策

### 1. 核心业务采用模块化单体

使用 **FastAPI + PostgreSQL** 建立统一业务 API。用 SQLAlchemy 组织持久化访问，Alembic 显式管理 schema 演进。

按身份、主体、账务、经营单据、结算、文件、汇总、提醒和同步划分模块。模块通过明确服务和命令协作，共享必要的数据库事务，不各自维护余额或费用副本。

不将第一版拆成多个独立部署的业务微服务；跨模块的财务一致性由统一模型与事务保证。需要独立资源的耗时识别采用 worker 进程，不因此为每个模块引入独立数据库。

### 2. 客户端共用业务契约

Web 使用 **React + TypeScript**，先实现中英文与手机布局的联网应用。后续 Android／iOS 使用 **Flutter**，接入同一套业务 API；账务规则留在统一业务层。

T03 负责稳定 ID、主体归属、版本、幂等键、金额字符串、修改游标和 tombstone 等契约目标。完整增量同步、冲突处理与移动端本地数据库属于 T11/T12，不把接口前缀 `/api/v1` 当作这些能力已完成的证据。

### 3. 长耗时 OCR 在本地独立 worker 中处理

API 接收并管理私有文件及任务；worker 在用户服务器内完成 PDF 文字提取／OCR，生成可核对的候选结果。人工确认通过业务服务入账。

worker 重试不能重复生成财务记录。具体模型、任务队列和存储实现需要样本与环境验证后确定，不在首 PR 引入未经验证的外部识别依赖。

### 4. 财务数据有单一事实来源

- 个人／公司 Entity、独立 Ledger 和多资产 Account 有明确归属；费用归属与付款账户所有者分开。
- Document／DocumentLine 表达业务及归属期间，Payment／Transfer 表达资金变动，Allocation 表达结算关系。
- 部分付款和多对多分摊不再产生额外收入／费用；个人代付之后的报销只结清往来。
- 内部以可验证的分录和审计结构维护一致性，前台使用简单收支操作。
- 跨主体合并只处理明确关联关系；给外部商家的付款不能因存在内部报销关系而被排除。

### 5. 原始数量与估值分离

采用精确 Decimal／NUMERIC 表示金额和资产数量，API 以十进制字符串传输。禁止先经过 JavaScript `Number` 或其他二进制浮点表示后再恢复精度。

账本记账基准币、实际成交金额、原币／资产数量、展示报价分别表达。历史与最新报价携带来源和时间，切换展示币种不改写交易或余额。每种资产使用适用精度，稳定币也使用行情估值。

### 6. 规则、私有文件及运行状态可追溯

文件需要授权访问，并与数据库一起进入可恢复备份范围。提醒规则保存适用条件、来源、核验时间和版本；人工覆盖保留，缺少参数时不猜测税务日期。

后台作业按业务类型设置幂等规则，区分生成草稿、实际入账、提醒投递和附件上传的状态。安全与基础备份前置，完整恢复演练在后续运维任务中验收。

## 首个 PR 的具体边界

当前代码仅建立以下内容：

1. `/api/v1/health/live`：进程存活检查，不访问数据库。
2. `/api/v1/health/ready`：通过 SQLAlchemy 执行 PostgreSQL `SELECT 1`，在连接异常时返回不可用状态。
3. 明确的环境配置、PostgreSQL 连接管理及有限的健康输出。
4. Alembic revision `20261003_0001`：空的迁移起点，没有业务表。

readiness 成功只说明该次数据库探测成功，不验证迁移状态或任何产品功能。生产模式关闭 API 文档不等于实现认证。当前没有用户登录、主体账本、财务写接口、私有文件访问、OCR、提醒、幂等存储或离线同步实现。

本决策确立后续实现方向，不能作为将 T01 整体或阶段 1–4 标为完成的依据。

## 备选方案

| 方案 | 当前未采用的原因 | 何时重新评估 |
| --- | --- | --- |
| 按业务拆微服务 | 单用户自部署阶段的运行与跨服务事务成本高；会放大付款、分摊、往来的一致性复杂度。 | 有明确独立部署、隔离或扩展需求，并已量化单体瓶颈时。 |
| 所有工作在 API 请求内同步执行 | OCR、PDF 处理和后台提醒耗时与资源需求不同，会影响请求延迟和可靠重试。 | 简单且可确定时长的轻量操作仍可直接执行，不把长任务塞入请求。 |
| 为 Web 和 App 建两套业务后端 | 会重复金额、账务、分类和权限规则，增加同步后的结果不一致风险。 | 暂无需要重复业务核心的理由；客户端可以有不同交互适配。 |
| 把全部业务数据作为前端本地唯一事实 | 不能直接满足首版在线 Web、服务器 OCR、统一后台提醒与后续多设备同步的共同要求。 | App 使用本地缓存及 outbox，但仍通过统一服务确认账务状态。 |
| 首 PR 一次引入完整业务与同步 schema | 已知功能多，过早固定全部表结构会在单据、代付和精度规则未经验证时扩大返工。 | T02/T03 按已确认案例逐步形成并验证实际 schema。 |

## 影响与约束

正向影响：

- 一套账务事实和明确事务边界便于验证余额、部分付款及代付不重复计费。
- 单体降低初期自部署的组件数量；本地 worker 可单独调整资源。
- Web 与 App 共用金额和版本契约，前期保留同步所需数据形态。
- 显式区分空工程基础与业务交付，后续人员可以根据仓库状态接续。

需要承担的约束：

- 必须持续维护模块边界，不能因共用数据库而允许所有模块任意修改账务表。
- 数据库迁移、共享 API 和财务规则由集成负责人统一协调。
- worker、周期任务和同步重试仍需要幂等设计，模块化单体本身不会自动提供这些能力。
- Flutter 离线编辑仍需认真处理版本冲突、删除传播、附件重试和设备缓存，不因共用 API 而自然完成。
- 本地 OCR 的准确率与吞吐量、提醒规则的适用性、完整备份恢复都需要实测或核验。

## 验证与后续决策

当前基础需分别验证进程存活与数据库故障路径，检查错误信息脱敏，并在明确配置的测试数据库上验证迁移入口。文档描述测试目标不等于测试已执行；结果统一记录到 [当前状态](../../engineering/status.md)。

后续实现遵循 [验收基线](../../product/acceptance.md)，优先验证部分结算、转账／报销不双计、精度、主体隔离及重复请求。OCR 资源与队列、文件后端、真实地区规则、同步冲突策略等在对应任务中另行形成可审阅的决定。

如需拆分服务、改变账务事实来源或跨端金额契约，新增 ADR 说明依据、迁移路径及受影响验收，不能静默偏离本决策。
