# ADR 0005：原子分录、期初与持久幂等回执

- 日期：2026-10-03
- 状态：采用；执行证据见 [当前状态](../../engineering/status.md)
- 任务：T02-3 与 T03，接续 [ADR 0003](0003-exact-asset-amounts.md) 和 [ADR 0004](0004-owned-ledger-structure.md)

## 问题

个人与公司已经有独立结构，需要在同一账户中记录多种资产的期初、收入和支出。金额拆分类别只能形成一次资金变化；网络重试不能再扣一次款。后续更正、票据匹配、部分结算与同步需要稳定的业务身份，不能把可变账户余额当作唯一事实。

## 业务身份与分录

`FinancialOperation` 提供稳定 UUID，`Journal` 保存不可变的一个修订，`JournalLine` 保存带方向的原币数量。业务对象保留当前分录指针；余额始终由全部已入账账户行求和，不能只把每项业务的当前修订相加。后续冲销需要原分录与反向分录一起参与余额。

本增量提供三种原子命令：

| 命令 | 账户行 | 对应行 | 限制 |
| --- | --- | --- | --- |
| 期初 | 指定的正数或负数 | 相反数量的期初权益行 | 每账户/资产只允许一个期初；零余额无需录入 |
| 收入 | 正数 | 一个或多个负数收入分类行 | 分类属于同账本收入类型；拆分正数之和等于总额 |
| 支出 | 负数 | 一个或多个正数费用分类行 | 分类属于同账本费用类型；拆分正数之和等于总额 |

每张分录至少两行，每行非零，按每个资产分别求和为零。不能把 100 USD 与 100 EUR 相互抵销。期初行不属于收入或费用。负账户余额允许存在，例如信用卡欠款；本增量不加入未要求的透支限制。

`transaction_date` 是实际收付款日，`recognition_date` 是业务归属日；手工收支显式提供二者，期初采用同一天。日期只能是 `YYYY-MM-DD`。T06 单据和结算仍须独立建模，关联已有付款不会再生成一次资金变化。

转账、信用卡还款属于 T02-4，换汇和独立手续费属于 T02-5，冲销/替代属于 T02-6。本增量没有这些占位接口。

## 精确数量与数据库约束

应用先根据不可变资产目录把十进制字符串解析为 `Amount`，以整数最小单位计算。`posting_storage.prepare_journal_lines` 检查行的实际 `asset_id`、完整资产定义、方向引用、范围和逐资产平衡，再产生 Decimal 参数；不会先转为浮点数。

数据库使用 `NUMERIC(38,18)`，另行校验有限数、20 位整数范围、资产精度和行引用。PostgreSQL 类型转换发生在 CHECK/触发器之前，因此原始 SQL 的超 18 位小数可能先被舍入；应用入口及绑定前检查负责拒绝原始过精度输入。数据库约束不是绕过应用金额入口的理由。

复合外键把账户资产、分类、分录和操作限定在同一账本。操作的当前分录指针采用延迟复合外键，允许同一事务创建相互引用的操作与分录。期初唯一标记和分录必须对应，不能给普通费用挂一个期初标记。

提交时的延迟约束检查完整分录并封存。只禁止 UPDATE/DELETE 仍会允许日后追加行，所以封存后也拒绝 INSERT 行。原始分录、行、期初标记及回执禁止修改或删除。将来的更正通过新分录实现。

## 并发与原子边界

财务写入按账本、主体、已排序资产的顺序加锁，与结构归档/停用流程协调。服务验证会话所有权，目标账户及资产关联启用、分类有效、主体未归档，然后检查拟写入后的每个账户资产余额范围。命令、分录、分类行、期初标记与幂等回执在同一数据库事务提交；任一步失败全部回滚。

同一账本的写入串行化是当前单用户系统的明确取舍，便于保证并发余额和结构修改一致。多账本不通过一个全局写锁阻塞。进一步细化锁之前必须保留并发回归用例。

## HTTP 与幂等合同

所有路径位于 `/api/v1/ledgers/{ledger_id}`，复用服务器会话、Origin 和 CSRF 检查。

| 方法与路径 | 用途 |
| --- | --- |
| `POST /opening-balances` | 设置一个账户资产期初 |
| `POST /income`、`POST /expenses` | 带分类拆分的手工收支 |
| `GET /operations`、`GET /operations/{operation_id}` | 有界列表或单项读取 |
| `GET /balances` | 原币余额，可按 `account_id` 筛选 |

POST 必须提供 `Idempotency-Key`：1–128 个不含空格的可见 ASCII 字符，作用域为账本。成功回执包含操作、分录 UUID、版本、原币金额字符串、分类拆分及两种日期；首次和成功重放都返回原来的 201 回执。

摘要包含命令类型、账本 ID 和验证后的请求体，JSON 键顺序不影响摘要。金额字符串不改变拼写，因此 `"1.0"` 与 `"1.00"` 是不同请求；同键不同请求返回 409。客户端重试应保留原始命令和键。可选客户端操作 ID 省略或 null 采用同一默认表示；服务端新生成的 UUID 不进入原请求摘要，重试时也不要把响应 ID 补进原先未指定 ID 的请求。

校验登录与账本所有权后，先检查持久回执，再执行新增命令的归档/启用检查。这样已成功请求在随后归档、停用或服务重启后仍可重放；新请求仍被拒绝。失败事务不保存成功回执。财务回执当前永久保留，没有会造成旧请求重新入账的短期 TTL。

列表 `limit` 为 1–200、`offset` 为 0–100000，采用稳定排序。余额包含已配置的零余额、已归档账户和停用资产关联，并附 `account_archived`、`asset_enabled`、`link_enabled` 标志；隐藏结构不会抹去资金。该接口不做行情估值或跨资产求和。

## 验证与运维影响

迁移 `20261003_0004` 显式增加五张财务表及其约束。迁移往返只在一次性测试库执行；有财务数据的回退不能直接降级删表，应使用已验证备份恢复方案。

验证覆盖 USD 100/EUR 80 期初后 USD 支出 25/EUR 收入 10 得到 75/90、加密资产精度、分类拆分、并发同键重放、异键重复期初、跨账本拒绝、无效命令回滚、余额上界、归档/停用重放和封存后不可补行。API 用真实会话连到 PostgreSQL，备份恢复在新空数据库上重读金额与回执，并再次验证封存保护。

集成测试的财务清理只在显式启用的一次性数据库夹具中执行受限 TRUNCATE；业务服务没有删除历史或禁用触发器的入口。实际已通过的测试以状态文档为准，设计条目本身不是执行证据。

## 备选方案

- 仅保存可变余额：无法可靠重建审计或校验分类与资金的一致性，未采用。
- 仅用内存去重：重启、恢复和多进程会丢失结果，未采用。
- 删除原记录再重写：破坏审计和重试语义，未采用；T02-6 使用冲销/替代。
- 金额文本语义等价即重放：会把精度错误与不同原请求混在一起；当前采用有文档说明的验证后请求体摘要。
