# ADR 0006：同资产转账与信用卡还款

- 日期：2026-10-03
- 状态：采用；实际验证见 [当前状态](../../engineering/status.md)
- 任务：T02-4 / T03，接续 [ADR 0005](0005-atomic-posting-and-receipts.md)

## 业务边界

同一账本两个不同账户之间移动相同资产，生成一笔 `transfer` 操作。转出账户扣减、转入账户增加相同原币数量；两边在一个事务中提交，不产生收入或费用分类行。跨主体转账与代付关系留给 T07，跨资产换汇与独立手续费留给 T02-5。

信用卡消费使用已有支出命令，信用卡账户余额减少；银行向信用卡还款使用相同转账命令，信用卡余额增加。欠款可表示为负数，不引入“全部账户不可为负”的假定。还款不会再记录一次消费费用。

## API 与回执兼容

`POST /api/v1/ledgers/{ledger_id}/transfers` 接收：

- 可选客户端 `id`，必填 `source_account_id`、`destination_account_id`。
- `asset_id`、正数十进制字符串 `amount`、`transaction_date` 和可选 `description`。
- 与其他财务命令相同的 Cookie、Origin、CSRF 和必填 `Idempotency-Key`。

转账的 `recognition_date` 采用交易日。首次和成功重放返回 201；同键异请求 409。原请求摘要规则不变，账户归档或停用后仍可重放已成功命令，但拒绝新增命令。

`TransferResponse` 使用明确的转出/转入账户字段，与已有 `OperationResponse` 通过 `kind` 组成判别联合类型 `FinancialResponse`。流水列表和单项读取返回该联合类型。已有期初、收入和支出回执保持原字段，没有新增无意义的空转入账户字段；旧持久回执仍按原结构解码。

选择不同回执类型是为了后续换汇明确表达两种资产和两项实际数量，避免同一个 `amount` 随操作类型隐含改变单位。

## 一致性约束

服务复用原有账本锁、所有权和回执事务；检查双方账户均属于当前账本、未归档、支持且启用当前资产。写入前同时检查两端结果余额的精确范围，任一端失败都不保存操作、分录或回执。允许正常负数余额。

数据库迁移 `20261003_0005` 扩展业务类型与提交校验函数，不新建表、不改写旧分录。转账必须恰好两条账户行、两个不同账户、同一资产、等量反向，并且没有期初标记和分类行。既有归属、精度、不可变与封存约束继续生效。

转出和转入在读取时由数量符号确定，不依赖行序号或创建顺序。新命令不能因为接口列表已经返回而丢失数据库事务提交错误。

## 迁移与验证

含转账历史时，迁移降级到 0004 明确拒绝；先锁定操作表再检查，防止检查与新写入竞态。没有转账记录的数据库可恢复原类型约束和原函数。迁移文件保存冻结的升级/降级 SQL，不导入以后可能变化的应用实现。

验证目标包括 A-04 银行 1000 转现金 200 后余额 800/200；A-06 信用卡消费 100 再还款，费用仍为 100、欠款归零；同键并发、反向并发、目标余额溢出整体回滚、归档重放和旧回执兼容。数据库独立测试不能配平、同账户伪转账、多资产、分类混入、错误日期及不安全降级。

备份恢复夹具在原精度数据外加入公司银行 1000、转现金 200、信用卡消费及还款 100，恢复后银行 700、现金 200、信用卡 0，费用只有 100。重放原转账回执和尝试向封存分录补行后，全部应用表应保持不变。实际通过证据记录在状态文档，本文不替代执行结果。
