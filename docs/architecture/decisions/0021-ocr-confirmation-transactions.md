# ADR 0021：票据草稿确认事务与原意图重放

- 日期：2026-10-08
- 状态：已采纳；按用户授权制定 T05-4 技术方案，不新增经营业务类型。
- 关联：[ADR 0012](0012-private-files-and-consistent-bundles.md)、[ADR 0014](0014-versioned-command-hashes.md)、[ADR 0015](0015-ordered-change-log.md)、[ADR 0020](0020-ocr-prefill-and-review.md)。

## 背景

识别任务已保留原件、原文、字段来源和逐行草稿。财务命令、文件关联目前各自提交事务，依次调用会留下“已入账但草稿未确认”的间隙。需要在保持旧财务 API、摘要和回执的前提下满足[需求 C-09/P-05](../../product/requirements.md)及[验收 B-01 至 B-04](../../product/acceptance.md)。

## 决定

- 确认是 OCR 模块的新命令外壳，不向现有财务请求加字段。它包含稳定意图 ID、源账本/草稿及预期版本、目标账本/文件、逐字段复核快照，以及“调用现有期初/收入/支出/转账/换汇”或“关联已有记录”的判别分支。不实现 Invoice、应收应付、结算或跨账本联合记账。
- 新增永久确认记录，保存所有者、源/目标归属、草稿、目标业务及文件引用、请求摘要版本/摘要、原回执和复核快照；同一草稿只能成功确认一次，同一账本意图只能绑定一个请求。成功后确认记录不可改删，草稿进入只读 confirmed；原识别结果和证据始终不改写。
- 新确认摘要采用 v2 的原始 JSON 规则，包含动作、路由和归属；缺省/null/空数组、数组顺序与金额字符串保持区别。内部财务命令使用由确认意图稳定派生的幂等键，把原始嵌套命令 JSON 交给现有 v2 入口，不能用补齐默认值后的模型重建原意图。已有 v1/v2 代码和回执不变。
- 完成身份和账本权限校验后先查确认回执；摘要相同原样重放，改变请求返回冲突。该步骤先于草稿版本、归档、字段复核及当前业务状态检查，恢复或后续修改不能令成功回执失效；重放不写表。
- 新确认使用单一外层事务：咨询锁 → 按稳定顺序锁全部涉及账本 → 主体 → 排序资产 → 草稿版本检查及其余引用。文件/任务只作归属和内容身份核对，识别及文件 IO 均在事务外。全部锁内重新校验，不依赖浏览器读到的快照。
- 在 OCR 模块提供私有的 session 绑定适配器复用 PostingService 和 DocumentService；默认服务入口不变，适配器只能使用同一所有者且已开启的外层事务，不能自行提交、回滚或关闭 Session。既有服务重入已取得的锁，不再取得顺序靠前的新锁。
- 新入账、附件关联、草稿状态、永久确认回执及变更日志一次提交；任何一步失败全部回滚。财务成功响应作为确认回执的一部分永久保存。关联已有记录仅增加证据与确认记录，要求目标业务及预期版本有效，不新增分录。
- 用户选择另一主体时，先通过现有两步上传流程把原件复制到目标账本，保留 File/上传 UUID 以恢复未知上传结果；确认事务检查目标文件与原件的哈希、大小、类型一致。保留所有复合外键，不跨账本直接引用同一个文件行；上传完成但确认失败不产生财务记录。
- 草稿编辑采用预期版本，保留与原候选分离的人工值及复核状态。所有需确认的字段必须逐项明确复核，缺失字段由用户填写；无 OCR 自动确认。文字层按现有规则预填，OCR 候选与原文同时显示；服务端再次验证复核路径集合及既有金额/日期/币种/分类约束。
- 单张票据分类拆分复用现有收支命令的总额校验，不建立另一套金额计算。逐行/批量确认由客户端对选中草稿顺序提交独立意图，已成功行保留；未知结果暂停后续提交并重放该行原意图，不静默生成新键。
- 同一草稿的并发确认只成功一次。相同原件/来源行已被其他草稿确认时提示已有记录并要求显式重复确认选择；金额和日期等相似信息只作提示，不自动合并或删除独立交易。复核与重复确认选择纳入原始请求摘要，不能在未知提交后静默改变。
- 确认与编辑接口沿用 Cookie/Origin/CSRF、归属校验及有界 JSON；金额始终为字符串。新增业务表接入变更日志，触发器保护归属、状态和不可变回执；有历史时拒绝降级。
- 网页仅在内存保存待提交原请求、键、上传 ID 和 File；会话过期保留原意图，同一用户重新登录后可重试，切换所有者不能提交别人的待办。刷新/关闭后的恢复以服务端草稿、确认记录和原业务回执核对，不使用本地持久化保存私有内容。

## 影响

按事务适配器、确认模型/迁移、复核与确认服务/API、网页及浏览器验收拆分。路由及字段契约由实现生成 OpenAPI 和前端类型；本决定不以占位接口或模拟入账代替完成能力。

验证整笔回滚、同键/不同请求、并发同草稿、旧回执跨归档/更正/恢复重放、跨账本引用拒绝、人工逐项复核、失败行重试、精确分类拆分及重复提示。验证备份后的草稿/原件/确认回执/财务一致，以及中英、桌面和 375/320 像素真实浏览器流程；不得仅用后端测试代替界面。

## 备选方案

- 先入账再更新草稿：失败间隙可能导致重复入账，不能原子恢复。
- 为 OCR 复制财务 SQL：形成另一套配平、历史与幂等规则，易破坏不变量。
- 向已有财务 DTO 加来源字段：会影响既有摘要及调用方；采用独立确认外壳和原命令复用。
- 仅靠客户端去重或自动按金额日期合并：不能处理并发/未知提交，也会误伤独立业务。
