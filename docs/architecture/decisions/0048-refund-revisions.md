# ADR 0048：真实退款更正、取消与永久回执

- 状态：提议（技术细化）。
- 日期：2026-11-09。
- 依据：P-03、B-11，ADR 0008、0012、0014、0015、0017、0040、0041、0043、0044、0045、0046、0047。

## 背景

真实退款记录实际资金流及独立手续费。贷项按手填净额、税额冲减原分类。录错退款时需要完整冲销，再按需要替代，同时保留原付款、明确引用的分摊退回、旧凭证和永久回执。
迁移 0036 的退款校验同时证明创建事实、原 201、退款操作 active/v1 和累计本金，退款形状也只按原凭证定位。修订需要分别证明历史上每版事实和今天仍占用的本金。

## 决定

### 固定来源与完整替代

- 固定退款、财务操作、账本、原付款，方向、往来及本金资产取自原付款。来源付款保持 active/v1 且当前凭证与原凭证相同。新命令的 `expected_version` 指退款操作版本，替代正文不得指定新身份或付款版本。
- 更正完整填写实际资金账户、资产、正数量、付款资产本金 `payment_amount`、交易日、退款事实说明、费用与有序退回引用。同资产两侧数量相等，跨资产显式填写两侧数量，按资产分别配平。退款本金只影响资金和往来，费用独立入账。
- 可显式替换同账本、同付款内已完整保存的退回引用及顺序。交易日不得早于付款及所引用的退回。费用最多 20 项，保留顺序与重复项。退回引用最多 200 项且互异，仅提供证据。两个列表省略或显式 `[]` 都表示清空，`null` 无效。
- 有效退款仍引用某次分摊退回时，退回取消须拒绝，即使付款剩余本金足够。先显式更正本退款的当前证据，再在写锁内重读全部有效引用及容量，方可判断退回能否取消。旧证据、原件及各版回执永久保留。
- 退款事实说明按原字符串最多 2000 个 Unicode 码点，再用 Python `strip()`。修订原因先 `strip()`，再限 1000 个码点。两者均拒绝空白和 NUL。新契约显式验证两侧本金及每笔费用均为正十进制字符串，最多 20 位整数、18 位小数。服务按实际资产校验精度，以最小单位计算，按 `NUMERIC(38,18)` 存储。旧创建及共享费用契约保持原义。
- 更正在同一操作下一版本写完整冲销和替代，取消仅写完整冲销并终止，操作指针保留最后一张正常凭证。接受严格整数版本，预期版本为 1 至 2147483646，结果恰加一。来源、分摊、余额或期间不允许修订时明确拒绝，原付款、分摊、退回和贷项各自保留。

### 不可变记录与回执

- 原退款、原费用、原退回引用和原 201 永久保留。追加修订快照和有序证据行，记录自身 UUID、同步版本 1、退款操作版本、同退款前驱、动作、原因、执行人、幂等键以及前一正常凭证、冲销凭证和可空替代凭证的映射。复合外键约束账本、退款、付款、同一操作和证据归属。
- 账本下的 `business-refunds/{refund_id}/corrections`、`cancellations` 使用独立动作，v2 摘要绑定动作、路由、账本、路径退款及收到的原 JSON。授权后先查账本幂等键，同键异意图冲突。金额拼写、原原因、列表顺序及省略与显式空列表之别均保留。旧创建动作、摘要和 201 响应不补字段。
- 新命令成功和重放均返回固定 200，含稳定身份、修订 ID、前后版本、动作、修订原因、三种凭证映射、完整 `previous` 和可空 `replacement`。两侧事实含实际资金及付款资产数量、来源版本、交易与归属日、事实说明、全部费用与有序证据。取消保留完整前版，替代事实和替代凭证均为空。
- 按修订 ID 和紧邻前版不可变事实证明完整 200，逐版核对状态码、摘要版本、操作锚点和原存储 JSON。SQL 区分整数 `2` 与 `2.0`，服务核对原 JSON 字典、严格整数和实际资产金额。历史重放先于归档、期间和当前容量检查，遇到损坏回执报错。

### 当前容量与原子写入

- 按账本和付款 ID 有界选取每笔退款的最新完整版本，再取有效本金。无修订取原版，取消贡献零，缺失或重复映射报错。用付款资产计量的可用本金为 `P − A − R`，P 是原付款本金，A 是分摊减明确退回，R 是所有有效退款本金。`applied_amount` 始终只表示 A，费用和证据不会放大 R。更正时令 `R_other = R − 本退款当前本金`，替代本金不得超过 `P − A − R_other`。
- 开放修订前三处使用同一投影：Python `settlement_totals.payment_totals`、SQL `coinpup_validate_business_refund` 和 `coinpup_validate_business_allocation` 的付款侧。冻结前一版本的分摊函数，保留其中的批量聚合、贷项净税和当前组容量校验。
- 在 READ COMMITTED 事务按写咨询锁、账本、主体、排序后的全部新旧资产加锁，读锁后新快照。原交易日与归属日、替代的两个日期均须开放，已结账须显式带理由重开。原付款及退回日期只作来源下界。
- 从当前封存凭证逐行精确反向现金、控制、exchange 和全部费用，保留日期、描述、组件及维度。旧停用引用可冲销。仅替代需验证新账户、资产、费用分类和原付款控制关联可用。复用既有退款计划、分录和余额校验，一次检验冲销加替代的最终余额。快照、行、操作头、固定 200 与变更通知同事务提交。
- 数据库分别证明原 v1 凭证及 201、按指定凭证唯一解析的每版 posting 事实、连续冲销和替代映射、每个历史 200、终态及当前本金。无修订时保留原 active/v1 拒绝规则。保留 0007 初始凭证、操作历史、冲销校验调用链和原延迟触发器。先在关闭提交的迁移层建立事实、容量与操作头守卫，再开放提交。直接 SQL 仅推进操作头或孤立取消须被拒绝。

## 影响

- 原退款列表、详情和普通财务入口保持既有语义。独立 current、分页版本目录与单版固定详情区分当前事实及历史。网页冻结用户、账本、退款、键和原正文，未知结果仅同键重放原意图。验收覆盖中英、桌面与手机、同用户重新登录、换用户清理以及迟到响应。
- 新表发布自身 UUID/版本 1 通知，稳定退款发布操作版本的 upsert/cancel，先取写咨询锁再分配序号。存在修订事实或对应历史通知时拒绝降级。空历史降级恢复精确前版 SQL。完整备份在空目标恢复 DB 和私有原件，复核事实、费用、证据、当前量及全部历史，逐一重放旧 201 和新 200 并验证零写入。
- 以虚构数据验收收付款双方向、同跨资产和第三资产费用、金额边界、连续更正后取消、原新期间、停用引用、同键同异意图、同版本竞争、并发分摊及退款容量、写入中断后整组回滚。直接 SQL 负例覆盖跨账本、错操作、缺前版或回执、不完整反向和取消复活。

## 备选方案

覆写原退款会破坏历史证据和回执。用普通收支或另一笔真实退款代替纠错会改变业务含义。自动调整分摊或贷项需要额外业务决定。每笔退款只有一个财务操作，沿既有单操作版本链可证明完整冲销及替代，复制贷项多成员组状态机会增添第二套身份和版本。
