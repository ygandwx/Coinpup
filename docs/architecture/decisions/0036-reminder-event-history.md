# ADR 0036：提醒事项与不可变修订历史

- 状态：已采纳（技术细化）
- 日期：2026-10-10
- 依据：P-07、C-08/C-10、ADR0015及0035。

## 背景

纯日期评估没有保存用户覆盖或完成状态。规则升级、公司资料变更与未知提交都需要可追溯的记录，不能只在一行中覆盖旧计算结果。

## 决定

- 新增账本内的`reminder_events`及`reminder_event_revisions`，分别保存事项当前状态和每个版本的完整快照。当前事项使用稳定UUID、版本条件更新与归档；主体经账本确定，不复制一套所有权关系。
- 事项类型为年审、税务申报或证件到期，身份/账本/类型和创建时间不可改。标题、说明、评估依据、人工日期、完成和归档状态的变化都推进版本并追加修订；禁止硬删除及修改/删除旧修订。
- 评估记录保存规则ID/版本/核验日期/来源、输入快照、状态和原因，推算日期与人工覆盖日期/理由分开。没有可采用的计算结果时，仍可保存待补充/待核验事项；不能伪造已确定期限。
- 新建、资料编辑、重算、设置/清除人工覆盖、完成/重开、归档/恢复使用明确动作。数据库保护版本连续和动作允许修改的字段；重算不能清除人工日期、修改完成/归档状态。清除人工覆盖须保留理由，回到当前有效推算值；计算仍待确认则没有可采用日期。
- 数据库在同一事务中为事项每一版本追加完整快照；修订的事项/账本复合外键、版本唯一键、快照与当前版本核对及不可变触发器共同防止伪造或缺失历史。当前状态和修订均接入变更日志。
- 非财务修改遵循咨询锁→账本→主体；不申请无关资产锁，不绕过账本归属。记录操作者，服务获取当前资料后才计算；纯日期计算本身无外部耗时调用。
- 未知创建结果按稳定UUID核对；未知更新保留原版本和正文，读取修订供人工核对。仅有字段或修订相同仍不足以证明原请求已执行，沿用显式版本冲突，不静默覆盖。网页接入时再细化原意图协议，不借用财务命令回执或改变既有v2命令。
- “事项完成”和后续的渠道投递成功分别记录；重算/规则升级不自动重开已完成事项。服务和任务不向已归档或已完成事项新增提醒计划；恢复归档也不隐式清除完成状态。

## 影响

先实现模型、冻结SQL迁移、直接SQL约束及完整bundle恢复证据，再接服务/API与双语网页。迁移接在当前单一Alembic head之后，有事项、修订或通知历史时拒绝降级；旧财务表和接口语义不变。

此模型保存选定事项及其修订，不提前建立经营单据提醒或年度批量生成任务。投递计划、渠道设置、SMTP未知结果和时区调度在单独协议中细化；外部发送不在数据库事务或锁内进行。

## 备选方案

只保存最新日期无法解释人工覆盖被谁改变，也无法核对未知更新。只在应用层追加审计会使直接SQL漏记历史；由数据库原子追加并保护修订更容易验证完整恢复和更新边界。
